# 经管之星 · 部署文档

> 本文对应 I6 的 T6-5。覆盖 Docker Compose 一键部署与本机开发两种路径。

## 一、环境要求

| 组件 | 版本 | 用途 |
| --- | --- | --- |
| Docker / Compose | 20.10+ / v2 | 一键部署（推荐） |
| Python | 3.11 | 本机开发 / 运行脚本 |
| Node.js | 20+ | 前端构建 |
| PostgreSQL | 15+ | 主库（含 `bi` schema 业务数据） |
| Redis | 7+ | 缓存、限流、问数结果缓存 |

最小资源：2 核 4G（问数链路本身不吃 CPU，瓶颈在大模型接口的网络往返）。

## 二、Docker Compose 一键部署

```bash
git clone <repo> && cd RdataAgent

# 1) 生成环境变量并**修改必改项**（见第三节）
cp .env.example .env && vi .env

# 2) 启动依赖服务（Postgres / Redis / MinIO）
cd deploy && docker compose up -d postgres redis

# 3) 建表 + 造数 + 只读账号授权（宿主机执行，需要本机 Python 环境）
cd .. && make venv deps
make seed          # 造数，生成 server/data/generated/*.csv
make db-init       # 建表 + 装载 CSV + 装载后校验（含只读账号授权）

# 4) 启动应用
cd deploy && docker compose up -d api web
```

访问：

| 服务 | 地址 |
| --- | --- |
| 前端 | http://localhost:5173 |
| 后端 API 文档 | http://localhost:8000/docs |
| MinIO 控制台 | http://localhost:9001 |

停止：`docker compose down`（数据卷保留）；连数据一起清：`docker compose down -v`。

### 部署后建议做一次缓存预热

```bash
make warmup-cache
```

原因见 README「性能优化」一节：冷缓存 P95 约 24s，预热后约 0.1s。

## 三、必改的环境变量

`.env.example` 里带的是本机开发默认值，**上生产前必须改这几项**：

```dotenv
# 1) 会话签名与密钥加密 —— 不改等于把门敞开
SECRET_KEY=          # 生成：openssl rand -hex 32
AES_KEY=             # 生成：openssl rand -base64 32（Fernet 要求）

# 2) 数据库口令（与 docker-compose 的 POSTGRES_PASSWORD 保持一致）
DATABASE_URL=postgresql+asyncpg://jingguan:<改成强口令>@postgres:5432/jingguan
BI_READONLY_URL=postgresql+asyncpg://bi_readonly:<改成强口令>@postgres:5432/jingguan

# 3) 运行环境：prod 会恢复严格的限流额度（非 prod 放宽 6 倍便于演示）
ENV=prod

# 4) 大模型
LLM_API_KEY=
LLM_BASE_URL=
LLM_DEFAULT_MODEL=
```

关于 `ENV`：非 `prod` 环境会把登录/接口限流额度放宽 6 倍（为了演示与自动化验证不被 429 打断）。
生产务必设为 `prod`。

关于只读账号：`BI_READONLY_URL` 是 Agent 取数专用的**只读**连接。
问数链路强制走它（`sql_guard` 还会再做一层语句白名单校验），
即使模型生成了 `DELETE`，也会在数据库层被拒。`make db-init` 会自动授权。

## 四、本机开发（无 Docker）

```bash
make setup-local        # 一键：生成 .env + 装依赖 + 起服务 + 造数 + 建表
make api-dev            # 后端 http://127.0.0.1:8000/docs
make web-dev            # 前端 http://127.0.0.1:5180
```

本机用的是 Homebrew 安装的 PostgreSQL 15 与 Redis（`make services-start`）。

## 五、Nginx 要点

前端容器用 Nginx 托管静态资源并反代 API。有一处**不能省**：

```nginx
location /api/v1/chat/completions {
    proxy_buffering off;      # 关闭缓冲，否则流式回答会攒成一坨再吐出来
    proxy_read_timeout 300s;  # 长问答（含自愈重试）需要放宽
}
```

配置文件在 `deploy/nginx/nginx.conf`，由 docker-compose 挂载进容器。
（Dockerfile 里不能 `COPY ../deploy/...`——那会越出构建上下文导致构建失败。）

## 七、常见问题

**问数一直转圈不出字**
先看后端日志是不是在等模型接口。若 `.env` 的 Key 无效，链路会逐个降级最后走兜底；
`make probe-models` 可以单独探测模型可用性。

**首次问数很慢，第二次飞快**
正常——命中了问数缓存（TTL 300s，可用 `QA_CACHE_TTL` 调整）。演示前跑 `make warmup-cache`。

**改了模型配置不生效**
模型路由是「数据库优先」：先看 `sys_model` 表里启用的模型，取不到才回退 `.env`。
在模型配置页切换默认模型**无需重启**，且切换动作会自动清空问数缓存。

**语义层指标停用后无法用同名重建**
这是有意的：保留历史问数的参照。查重只与启用中的记录比对，换一个 code 即可。

## 八、已知未覆盖

- **Docker 镜像构建未在本机实测**：开发环境没有安装 Docker，
  `docker-compose.yml` 与两个 Dockerfile 是按规范编写的静态配置，
  首次部署时若遇到构建问题，优先检查 `server/Dockerfile` 的依赖安装环节。
- **无 CI 流水线**：当前验证靠 Makefile 里的脚本（`make test` / `check-*`）手工执行。
- **未做水平扩展**：应用无状态（会话在 JWT、缓存在 Redis），
  可以同时跑多份 API 实例，但需要额外加负载均衡，且 `make db-init` 只应执行一次。
