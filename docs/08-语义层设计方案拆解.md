---

## 0. 一句话定位

语义层 = **受控子集 + 口径契约 + 经验库** 三合一的元数据层。它把「对着 60+ 列宽表做开放生成」这个不可控问题，收敛成「在已注册的表达式里做选择题」。

```3:7:server/scripts/check_semantic.py
    Text2SQL 的失败大多不是"模型笨"，而是语义层给的配方本身有问题——
    expr_sql 引用了表里不存在的列，或规则里的时间/口径写法只覆盖某一张表。
    模型拿到错误配方只能硬凑，表现为 column "xxx" does not exist，
    或更糟：SQL 能跑但数字不对。这类问题靠等用户报错来发现太被动。
```

这段话是全项目的设计判断：**准确率的天花板由语义层决定，不由模型决定。**

---

## 1. 为什么需要它

| 没有语义层（裸表 Text2SQL） | 有语义层（本方案） |
| --- | --- |
| 60+ 列 DDL 全塞 Prompt → 上下文膨胀 + 列名幻觉 | 只注入被选数据源关联的指标/维度，Prompt 控在 2k token |
| 「收入」是哪列？含税还是不含税？分摊还是落地月？模型猜 | `expr_sql` 写死 `SUM(f.year_income)`，`caliber` 说明口径 |
| 完成率加权还是简单平均？每次答案可能不同 | `sem_rule` 写死加权口径，附实测反例 |
| JOIN 关系靠推断，维表别名每次都不同 | `join_sql` + 全局 `ALIASES` 别名契约 |
| 错一次就错一次，无沉淀 | `sem_fewshot` 沉淀 verified 样本，相似度召回 |
| 安全校验无从下手 | `allowed_tables` 由语义层反推，白名单天然成立 |

---

## 2. 元模型：六张表各司其职

```
sem_data_source ─┬─< sem_metric      （这个数据源上能算什么）
                 └─< sem_dimension   （能按什么拆、怎么 JOIN、有哪些取值）
sem_rule                              （跨数据源的强制业务规则）
sem_fewshot                           （问答-SQL 经验库）
sem_dict_column                       （列级数据字典：台账页 + 语义层复用）
```

### 2.1 `sem_data_source` —— 作用域与安全边界

```13:22:server/scripts/sql/002_schema_sem.sql
CREATE TABLE IF NOT EXISTS sem_data_source (
    id          BIGSERIAL PRIMARY KEY,
    group_name  VARCHAR(64)  NOT NULL,        -- 台账数据 / 统计报表
    name        VARCHAR(64)  NOT NULL,        -- 商业市场台账
    object_name VARCHAR(128) NOT NULL,        -- bi.fact_contract / bi.v_overall_achieve
    object_type VARCHAR(16)  NOT NULL,        -- table / view
    description TEXT,
    enabled     BOOLEAN      NOT NULL DEFAULT TRUE,
    sort_order  INT          NOT NULL DEFAULT 0
);
```

- **唯一的裁剪入口**：用户勾选「整体达成」→ 只注入 `source_id=4` 的指标维度，其余不进 Prompt。
- **同时是安全边界**：`enabled=0` 的数据源既不进 Prompt，也不会出现在 `allowed_tables` 白名单，等于一键下线。
- `object_type` 区分 table/view，为「视图优先」规则（rule #18）埋伏笔。

当前 9 个：3 张事实表（contract / ppl / goal）+ 6 个报表视图。

### 2.2 `sem_metric` —— 口径固化的核心

```24:37:server/scripts/sql/002_schema_sem.sql
CREATE TABLE IF NOT EXISTS sem_metric (
    id             BIGSERIAL PRIMARY KEY,
    code           VARCHAR(64) NOT NULL UNIQUE,
    name           VARCHAR(64) NOT NULL,
    aliases        JSONB       NOT NULL DEFAULT '[]'::jsonb,
    expr_sql       TEXT        NOT NULL,
    source_id      BIGINT      NOT NULL REFERENCES sem_data_source (id),
    unit           VARCHAR(16) NOT NULL DEFAULT '万元',
    value_type     VARCHAR(16) NOT NULL DEFAULT 'decimal',
    agg_default    VARCHAR(16) NOT NULL DEFAULT 'SUM',
    caliber        TEXT,
    default_format VARCHAR(32) DEFAULT '#,##0.00',
    enabled        BOOLEAN     NOT NULL DEFAULT TRUE
);
```

**最关键的设计决策：`expr_sql` 存完整聚合表达式，而非裸列名。**

| 存法 | 模型自由度 | 风险 |
| --- | --- | --- |
| 裸列名 `year_income` | 自己决定 SUM/AVG、是否 CASE WHEN | 口径漂移，同一问题不同答案 |
| **表达式 `SUM(f.year_income)`** | 只能整体引用 | 口径唯一 |

真实样本：

```29:31:server/scripts/sql/005_seed_semantic.sql
(1,  'biz_income',        '商业收入',       '["收入","营收","签约额","销售额","商业收入","收入额"]'::jsonb,
     $sql$SUM(f.year_income)$sql$, 1, '万元', 'decimal', 'SUM',
     '商业收入 = 不含税签约额，取台账已确认的年度收入（分月收入之和）', '#,##0.00', TRUE),
```

```44:45:server/scripts/sql/005_seed_semantic.sql
     $sql$ROUND(SUM(f.gross_profit) / NULLIF(SUM(f.amount), 0) * 100, 2)$sql$, 1, '%', 'decimal', 'NONE',
     '毛利率 = 毛利 / 合同金额 × 100，除数为 0 返回 NULL', '#,##0.00', TRUE),
```

毛利率这类**复合指标被整体冻成一个字符串**——模型不需要知道分母是 `amount` 还是 `year_income`（真实踩过的坑，rule #9 专门写「毛利率分母是金额不是收入」）。

其余字段：
- `aliases` JSONB：中文同义词表（「营收/签约额/销售额」→ `biz_income`），是槽位抽取与改写的匹配依据。
- `unit` / `default_format`：进 Prompt，让模型知道输出「万元」还是「%」。
- `agg_default`：`NONE` 表示已是比率，不可外层再 SUM。
- `caliber`：人话口径，**同时给模型看和给运营在管理页看**，一份文档两处复用。

### 2.3 `sem_dimension` —— 拆分维度 + JOIN 契约

```40:52:server/scripts/sql/002_schema_sem.sql
CREATE TABLE IF NOT EXISTS sem_dimension (
    id           BIGSERIAL PRIMARY KEY,
    code         VARCHAR(64) NOT NULL UNIQUE,
    name         VARCHAR(64) NOT NULL,
    aliases      JSONB       NOT NULL DEFAULT '[]'::jsonb,
    expr_sql     TEXT        NOT NULL,
    display_expr TEXT,
    join_sql     TEXT,
    source_id    BIGINT      NOT NULL REFERENCES sem_data_source (id),
    dim_type     VARCHAR(16) NOT NULL DEFAULT 'categorical',   -- categorical / time / numeric
    value_map    JSONB,
    enabled      BOOLEAN     NOT NULL DEFAULT TRUE
);
```

四个字段是这块设计的精华：

**① `expr_sql` 与 `display_expr` 分离 —— 分组键与展示列解耦**

```87:91:server/scripts/sql/005_seed_semantic.sql
(1,  'unit',         '经营单元', '["办事处","代表处","单元","组织","经营单元","部门"]'::jsonb,
     $sql$f.unit_code$sql$, $sql$d.unit_name$sql$,
     $sql$LEFT JOIN bi.dim_unit d ON d.unit_code = f.unit_code$sql$, 1, 'categorical',
     -- 按区域分组的经营单元清单：多轮改写据此识别「北京」→「北京代表处」
     '{"华北":["北京代表处","山西办事处","辽宁办事处","泛政府系统部"],...}'::jsonb, TRUE),
```

`GROUP BY f.unit_code`（性能好、无歧义）+ `SELECT d.unit_name`（人能读）。模型自己写八成会直接 `GROUP BY unit_name`。

**② `join_sql` 是完整 LEFT JOIN 片段**，不是「关联哪张表」这类抽象描述。模型直接抄，不需要推断 ON 条件。

**③ `value_map` 是多轮对话的燃料**（最容易被忽略的字段）：

```189:199:server/app/agent/nodes/retrieve.py
def _dim(d: SemDimension) -> dict:
    # value_map 是多轮改写抽取「主体 / 筛选」的依据，缺了它指代消解会完全失效
    return {
        "code": d.code,
        "name": d.name,
        "aliases": list(d.aliases or []),
        "expr_sql": d.expr_sql,
        "display_expr": d.display_expr or "",
        "join_sql": d.join_sql or "",
        "dim_type": d.dim_type,
        "value_map": d.value_map,
    }
```

注意 `unit` 的 value_map 是**按区域分组的嵌套结构** `{"华北":[...],"华东":[...]}`，而 `region` 是扁平数组。改写模块用 `_flatten_values()` 统一摊平。

**④ `dim_type`** 区分 categorical/time/numeric，让时间维度走专门解析而非普通取值匹配。

### 2.4 `sem_rule` —— 反例驱动的口径护栏

```55:62:server/scripts/sql/002_schema_sem.sql
CREATE TABLE IF NOT EXISTS sem_rule (
    id       BIGSERIAL PRIMARY KEY,
    scene    VARCHAR(64)  NOT NULL,     -- time / caliber / ranking / chart
    title    VARCHAR(128) NOT NULL,
    content  TEXT         NOT NULL,
    priority INT          NOT NULL DEFAULT 0,
    enabled  BOOLEAN      NOT NULL DEFAULT TRUE
);
```

**这是整个语义层工程价值最高的一张表**——它不是正面描述业务，而是**把踩过的坑连同实测数字一起写进去**。rule #7「完成率口径」：

```175:185:server/scripts/sql/005_seed_semantic.sql
(7,  'caliber', '完成率口径',
     $txt$完成率 = 收入 / 目标 × 100，保留 2 位小数；除数为 0 时用 NULLIF 返回 NULL，不得报除零错误。
⚠️ 跨多个经营单元的「整体完成率」必须用 SUM(income) / SUM(biz_goal) × 100（以目标额为权重的加权口径）。
请直接查 bi.v_overall_achieve 视图，它已按经营单元聚合好 income 与 biz_goal：
  SELECT ROUND(SUM(income) / NULLIF(SUM(biz_goal), 0) * 100, 2) FROM bi.v_overall_achieve WHERE year = YYYY

两个会导致结果完全错误、必须避免的写法：
1) 不要对视图的 achieve_rate 列直接 AVG —— 那是各单元的简单平均，与单元目标大小无关。2026 年实测：加权 84.82% vs 简单平均 79.83%，相差约 5 个百分点。
2) 不要把 bi.fact_contract 与 bi.fact_goal 直接 JOIN 后再 SUM —— ...2026 年实测：目标合计被放大约 585 倍（84,485,632 vs 真实 144,256），完成率算出 0.14% 而非 84.82%。若确需明细级关联，必须先各自按 unit_code 聚合再 JOIN。
```

「放大 585 倍」这种带实测数字的**反例**，比任何正面描述都更能约束模型——这是语义层运营沉淀的真实形态。

rule #5「时间列按表区分」同样硬核，直接列出每张表有哪些日期列、**并明确写出不存在的字段**：

```154:158:server/scripts/sql/005_seed_semantic.sql
3) bi.fact_goal（别名 g）：只有年度 g.year 与月份 g.month（integer，取值 0-12）。该表【没有任何日期列】，不存在 land_date、month_date、goal_date 之类字段——不要臆造。按月查目标直接用 g.month 分组，例如 GROUP BY g.month；不要写 EXTRACT(MONTH FROM g.月份)。
⚠️ 关于 g.month = 0：它是【年度汇总行】（每个经营单元一行，其 biz_goal 等于该单元 1-12 月之和）。因此查「全年目标/总目标」用 WHERE g.month = 0；查「各月目标分布」用 WHERE g.month BETWEEN 1 AND 12。绝不可在不限定 g.month 的情况下 SUM(g.biz_goal)，否则汇总行与明细行相加，结果正好翻倍。
```

`scene` 四类（time/caliber/ranking/chart），`priority` 降序注入。运行时只取 `scene='caliber'` 的第一条做第①步的展示文案。

## 3. 运行时：语义层在每一步怎么被消费

```
用户问题
  ├─ ① intent.classify()              纯正则 9 类意图，不查语义层
  │                                     chitchat / out_of_scope → 直接模板回复
  ├─ ② retrieve_schema(db, source_ids) ★ 语义层裁剪 + 推导 allowed_tables
  ├─ ③ rewrite()                       ★ 用 aliases + value_map 做槽位抽取与指代消解
  │                                     「那北京呢」→「2026年北京代表处商业收入」
  ├─ ④ sql_generate()                  ★ schema.render() 进 Prompt + Few-shot Top-3 召回
  ├─ ⑤ sql_validate()                  ★ allowed_tables 白名单 + LIMIT + 行级权限注入
  │                                     失败 → retry_hint 自愈重试（最多 2 次）
  └─ ⑥ 执行 → chart_advisor → compose
```

### 3.1 裁剪：`retrieve_schema`

```107:116:server/app/agent/nodes/retrieve.py
async def retrieve_schema(
    db: AsyncSession,
    source_ids: Optional[list[int]] = None,
) -> SchemaContext:
    """按选中的数据源裁剪语义层。source_ids 为空表示全部。"""
    src_stmt = select(SemDataSource).where(SemDataSource.enabled.is_(True))
    if source_ids:
        src_stmt = src_stmt.where(SemDataSource.id.in_(source_ids))
    sources_rows = (await db.execute(src_stmt.order_by(SemDataSource.sort_order))).scalars().all()
```

细节：勾选的数据源若全被停用，**兜底回到全部启用数据源**，而不是返回空 Schema 让链路崩掉。

### 3.2 白名单：`allowed_tables` 由语义层反推

```49:58:server/app/agent/nodes/retrieve.py
    @property
    def allowed_tables(self) -> list[str]:
        """SQL 表白名单 = 数据源对象 + 维表（维表来自维度的 JOIN 语句）。

        维度表必须放行，否则模型写出的 JOIN 会被安全校验误杀。
        """
        names = {s["object_name"] for s in self.sources}
        for d in self.dimensions:
            names.update(_JOIN_TABLE_RE.findall(d.get("join_sql") or ""))
        return sorted(names)
```

**语义层与安全层的关键接口**。维表（`bi.dim_unit` 等）不在 `sem_data_source` 里，是通过维度的 `join_sql` 引入的——必须用正则从 `join_sql` 抠出 `bi.xxx` 放行。少了这步，模型按语义层教它的 JOIN 写出的 SQL 会被自己的安全校验误杀。

### 3.5 指代消解：语义层驱动的多轮改写

槽位抽取完全基于语义层的 `aliases` 与 `value_map`：

```120:141:server/app/agent/nodes/rewrite.py
    # 指标（含别名）
    for m in schema.metrics:
        names = [m["name"], m["code"], *(m.get("aliases") or [])]
        if any(n and n in q for n in names):
            s.metrics.append(m["code"])
    # 维度（含别名）
    for d in schema.dimensions:
        names = [d["name"], d["code"], *(d.get("aliases") or [])]
        if any(n and n in q for n in names):
            s.dimensions.append(d["code"])

    # 主体 / 筛选：命中维度取值表
    # 只有「主实体」维度（经营单元、区域、客户、销售）的取值才构成分析主体；
    # 行业、产品线等维度取值一律只作为筛选条件叠加，避免覆盖上文主体。
    for d in schema.dimensions:
        # 时间由 time_range 单独建模，再生成 year 筛选会与「2026年」重复
        if d["code"] == "year":
            continue
        for v in _match_values(q, _flatten_values(d.get("value_map"))):
            s.filters.append({"dim": d["code"], "op": "=", "value": v})
            if d["code"] in SUBJECT_DIM_CODES:
                s.subject = v
```

三个值得学的设计：

**① 主体与筛选分离**。`SUBJECT_DIM_CODES` 白名单：

```26:27:server/app/agent/nodes/rewrite.py
# 只有这些维度的取值才被视作「分析主体」（其余维度取值只作筛选）
```

### 3.6 Few-shot 召回：2-gram Jaccard（非向量）

```143:168:server/app/agent/nodes/sql_generate.py

        if r[3]:

        scored.append((score, r))
```

打分逻辑：

```33:40:server/app/llm/template_provider.py
def similarity(q1: str, q2: str) -> float:
    """基于 2-gram 的 Jaccard 相似度。"""
    a, b = _tokens(q1), _tokens(q2)
    if not a or not b:
        return 0.0
    inter = len(a & b)
    union = len(a | b)
    return inter / union if union else 0.0
```

**取舍分析**：
- 优点：零依赖、无 API 调用、无额外延迟、中文无需分词库（`_STOP` 停用词表 + 2-gram）。
- 代价：**语义等价但字面不同的问法召回不到**（「今年卖了多少」vs「2026年商业收入」）。
- `embedding BYTEA` 字段已预留，升级路径清晰。

`verified` 的 ×1.05 是**轻微加权**而非硬排序——设计上刻意让人工样本只在同分时占优，不压制新问题。

### 3.7 降级路径：语义层即「无 LLM 的兜底引擎」

```1:9:server/app/llm/template_provider.py
"""检索式兜底 Provider（无需 API Key）。

定位：技术方案 §11.4 的降级路径之一——模型不可用 / 未配置 Key 时，

```

阈值 `0.18`，低于则抛错走正常链路。这是**语义层的隐藏价值**：它不只提升准确率，还让系统在 LLM 完全不可用时仍能演示与自测。

## 4. 六大关键设计决策与取舍

| # | 决策 | 收益 | 代价 / 风险 |
| --- | --- | --- | --- |
| 1 | 存 `expr_sql` 而非列名 | 口径唯一，复合指标零漂移 | 指标不可组合（无法动态 SUM(A)/SUM(B)），新指标必须运营录入 |
| 2 | 全局 `ALIASES` 别名契约 | SQL 稳定可读，JOIN 可预测 | 别名表与 `check_semantic.py` 各存一份，改一处要改两处 |
| 3 | `allowed_tables` 由语义层反推 | 安全白名单与生成能力同源，不会误杀合法 JOIN | 正则抠 `bi.xxx` 脆弱；跨 schema 表名会漏 |
| 4 | `value_map` 驱动指代消解 | 多轮对话可用，且取值由运营维护 | 取值多时 value_map 手工维护成本高（model 维度直接置 NULL） |
| 5 | 2-gram 相似度而非向量 | 零依赖零延迟 | 语义相似召回不到；样本量增大后全表扫描变慢 |
| 6 | 软删除 + 幂等 upsert 种子 | 历史问数记录不失去参照；种子可反复执行 | 停用指标的 code 可复用，查重需带 `enabled` 条件 |

## 7. 亮点与改进建议

### 亮点

1. **口径以「表达式 + 反例 + 实测数字」三重固化**——`expr_sql` 保证唯一，`sem_rule` 的「放大 585 倍」类反例防止模型自作聪明。这是本项目最值得复制的经验。
2. **语义层同时是安全边界**：`allowed_tables` 由它推导，白名单与生成能力天然同源，不存在「能生成但被拦」或「放行但没教过」的错位。
3. **无 Key 也能跑通全链路**：`TemplateProvider` 把 Few-shot 库当降级引擎，语义层的价值不止于提准确率。
4. **体检脚本把「等用户报错」变成「主动发现」**，特别是覆盖度报告直接指导补录。
5. **软删除 + 幂等 upsert + 按资源鉴权 + 审计**：运营侧工程完备度超出一般 Demo。

### 改进建议（按性价比排序）

1. **缓存键加入语义层版本号**。`sem_metric` / `sem_rule` 任一行变更即 bump 版本号（或用 MAX(updated_at) 摘要），否则「改了口径但答案没变」会成为最难排查的线上问题。当前 `sem_metric` 甚至没有 `updated_at` 字段，建议补上。

2. **点踩自动生成 Few-shot 候选**。人工闭环的瓶颈在于运营要主动去翻工单。点踩时若同时命中高置信度样本，可自动生成一条「待修正样本」（verified=false）挂到工单上，把闭环从「人找问题」变成「问题找人」。

3. **Few-shot 召回升级为向量**。`embedding BYTEA` 已预留，样本 50 条时全表扫描还扛得住，到几百条就该切 bge-m3 或 pgvector。建议保留 2-gram 作为向量不可用时的降级。

4. **别名表去重**。`retrieve.py` 的 `ALIASES` 与 `check_semantic.py` 的 `ALIASES` 是两份硬编码，已存在漂移风险（注释里也承认「与 agent/nodes/retrieve.py 的 ALIASES 保持一致」）。建议落到 `sem_data_source` 的一列或独立配置表。

5. **指标组合能力**。当前复合指标必须整体注册，无法表达「A/B 比率」这类临时组合。可考虑引入 `sem_metric.derived_from`（引用其它 metric code），让模型在受控范围内做有限组合。

6. **`sem_dict_column` 与问数链路打通**。表注释写明「FR-D4：供问数语义层复用」，但目前只服务台账页。可在 `expr_sql` 校验时用它做列存在性的二次确认，或为未覆盖列自动生成维度候选。
