## 2. 迭代详细计划

### I0 · 地基与造数（W1，约 14.5 人日）

**目标**：工程骨架 + 全量数据结构 + 数据就绪，为后续迭代扫清依赖。

| 编号 | 任务 | 角色 | 人日 |
| --- | --- | --- | --- |
| T0-1 | 仓库初始化（web/server/deploy）、代码规范（ruff/eslint/prettier）、CI 骨架 | 后端 | 1 |
| T0-2 | FastAPI 骨架：配置、日志、异常、健康检查、OpenAPI | 后端 | 1 |
| T0-3 | PostgreSQL + Redis + MinIO docker-compose；双账号（读写/只读） | 后端 | 1 |
| T0-4 | 全量 DDL + Alembic 迁移（`sys_*`/`chat_*`/`sem_*`/`bi.*`） | 后端 | 2 |
| T0-5 | 报表视图 `v_*` × 5 + 索引 + ANALYZE | 后端 | 1 |
| T0-6 | 造数：维度表 + `fact_goal` + `fact_contract` + `fact_ppl` | AI | 3 |
| T0-7 | 造数：系统数据（用户/角色/菜单/权限/预置会话/反馈/日志） | 后端 | 1.5 |
| T0-8 | 造数一致性校验脚本 + `make seed` 一键执行 | AI | 1 |
| T0-9 | Vite + React + TS + AntD + 路由骨架 + 设计令牌 | 前端 | 2 |
| T0-10 | 语义层初始内容（18 指标 / 12 维度 / 15 规则 / 20 Few-shot） | AI | 2 |

**交付物**：可 `docker compose up` 的骨架；`make seed` 生成 6.2 万行数据；前端空壳可路由。
**验收**：数据一致性断言全绿；`v_overall_achieve` 查询 < 200ms；前端占位页可访问。

**⚠️ 决策点 D1**：若基线 < 60%，立即投入 3 天做 Prompt 与语义层重构，并评估是否更换主模型。

### I3 · 多轮对话与准确率调优（W6–W7，约 29.5 人日）

**目标**：把「能问」升级为「会聊」——本项目的技术制高点。

| 编号 | 任务 | 角色 | 人日 |
| --- | --- | --- | --- |
| T3-1 | Slots 模型 + 合并策略 + SessionContext（Redis） | AI | 2.5 |
| T3-2 | ContextRewriter：规则引擎（指代/时间/条件词） | AI | 3 |
| T3-3 | ContextRewriter：轻量 LLM 兜底 + 澄清反问机制 | AI | 2 |
| T3-4 | IntentClassifier（9 类意图）+ 分流转发的 5 条策略 | AI | 2.5 |
| T3-5 | 结果二次加工（`result_ops`：排序/改图/翻页/导出） | AI+前端 | 3 |
| T3-6 | 长对话摘要压缩（>6 轮） | AI | 1.5 |
| T3-7 | SelfChecker 自愈重试（语法错误/空结果/异常值） | AI | 2.5 |
| T3-8 | 评测集建设：100 条问答对（9 类意图）+ 执行结果比对脚本 | AI+测试 | 3 |
| T3-9 | 准确率调优：Few-shot 扩充至 50 条 + 规则补充 + Prompt 迭代 | AI | 4 |
| T3-10 | 越界拒答 + 闲聊回复 + 低置信提示 | AI | 1.5 |
| T3-11 | 前端：澄清卡片、追问 chips、编辑重发、重新生成、上下文展示 | 前端 | 3 |
| T3-12 | 多轮 E2E 用例（UC-2 五轮追问） | 测试 | 2 |

**交付物**：多轮对话完整能力 + 评测体系。
**验收**：**UC-2 通过**；评测集一次执行成功率 ≥ 90%；多轮指代消解正确率 ≥ 85%；`result_ops` 响应 < 1s。
**⚠️ 决策点 D2**：若成功率卡在 85% 无法突破，启动「人工 Few-shot 运营」——把失败用例人工写出正确 SQL 并标 `verified=true`，通常 1~2 天可拉升 5~8 个百分点。

## 5. 精简版排期（5 周 MVP，适合 1~2 人小团队）

> 前提：1 名全栈（偏后端）+ 1 名全栈（偏前端）；1 人独立开发则工期 ×1.8

| 周次 | 主题 | 内容 | 交付 |
| --- | --- | --- | --- |
| **W1** | 骨架 + 造数 | 复用本方案 DDL 与造数脚本；FastAPI + Vite 骨架；PostgreSQL/Redis 起容器 | 数据就绪、空壳可跑 |

### B-1 ~ B-7 详情（问数链路技术债）

来源：2026-08-31 源码走查，逐条定位见 `docs/07-问数链路与启动流程.md` 第 1.7 节。
共同特点：**不影响单副本演示环境**，但在生产场景或代码维护上会持续产生成本。

**B-1 Redis 降级后多 worker 会话上下文不共享** ⚠️ 优先级最高

- **现象**：`core/redis.py:17` 的 `_memory` 是**进程内**字典。Redis 不可用时，
  会话上下文（`active_slots` / `last_sql` / `last_result_key`）只存在于当前进程。
- **影响**：多 worker（`uvicorn --workers N`）或多副本部署时，同一会话的追问可能被
  负载均衡打到另一个进程，取不到 `prev_slots` → 追问丢失时间范围与指标 → 结果与上文对不上。
- **为什么演示环境看不出**：单进程单副本，所有请求都落在同一个 `_memory` 上。
- **建议方案**（三选一）：
  1. 降级时直接禁用多轮（追问走澄清流程），宁可显式失败也不静默出错；
  2. 把会话上下文落到数据库（已有 `chat_session` 表，可加 JSON 列）；
  3. 部署层面强制要求 Redis 可用（健康检查里加 `redis.is_degraded()` 断言）。

**B-2 `ctx.summary` 已生成但从未注入 Prompt**

- `runtime.py:404 _update_summary` 每轮都维护摘要（保留最近 8 行），
  `context.py:98 needs_summary` 也实现了阈值判断（`turn_count > 6`），
  但 `runtime.run` 中**没有任何地方把 `ctx.summary` 注入 Prompt**。
- **影响**：超过 6 轮后，早期轮次的上下文只靠 `_build_history` 的 12 条窗口维持，
  更早的内容彻底丢失，而摘要机制形同虚设。
- **修复**：在 `generate_sql` 的 `user_parts` 中追加 `【更早对话摘要】\n{ctx.summary}`
  （当 `needs_summary(ctx)` 为真时）。

**B-3 `_pick_fewshots` 每次问数全表扫描**

- `sql_generate.py:131-140`：每次问数都 `SELECT` 全部 `sem_fewshot`，
  在内存里算 2-gram 相似度后排序，且未做 `enabled` 过滤。
- **影响**：当前 50 条尚可接受，样本增长到数百条后每次问数都有固定开销。
- **修复**：加 `enabled` 过滤；或预先把 question 向量化后落库，用 DB 侧相似度检索。
- **建议**：与 T5-7（后端性能）合并处理。

**B-4 `chat_query_trace` 表已定义但无写入**

- `app/models/__init__.py:277-287` 定义了表（trace_id / step / status / detail / cost_ms），
  但全库无 INSERT。
- **现状**：trace 实际靠 `chat_message.trace_id` + `payload['steps']` + 结构化日志留存，功能上够用。
- **修复**：二选一——补写入（可观测更完整，配合 T5-9）或删表（消除误导）。

**B-5 `intent` 事件后端发送、前端无消费**

- `runtime.py:117` 发 `intent` 事件；`AiQa/index.tsx:200` 的 switch 无对应 case，被静默丢弃。
- **修复**：二选一——前端加 case（可用于展示「识别为：排名类问题」）或后端停发（省一个事件）。

**B-6 `rewrite()` 的 `history` 形参未被使用**

- `rewrite.py:251` 声明了 `history: str = ""`，函数体内无任何引用。
- **注意**：这**不是**多轮继承的缺陷——继承靠 `ctx.active_slots` 结构化槽位完成，工作正常。
  只是这个参数会误导阅读者以为历史文本参与了改写。
- **修复**：删除形参，或补注释说明「刻意不使用」。

**B-7 `result_ops` 分支重复调用 `cache_result`**

- **影响**：功能无影响（同一毫秒内返回相同 key，内容相同），但产生一条无用 Redis 键。
- **修复**：删掉第 143 行。
