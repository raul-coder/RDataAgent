## 1. 方案总览

### 1.1 设计原则

| 原则 | 落地做法 |
| --- | --- |
| 以「语义层」而非「裸表」喂给 LLM | 指标/维度/口径/同义词全部注册为元数据，Text2SQL 只针对受控子集生成，命中率与可控性远高于直接给 60 列宽表 |
| 过程可解释优先于结果炫技 | 5 步链路（选表→推理→SQL→结果→结束）是产品契约，每一步都由 Agent 真实产出，不是前端假动画 |
| 多轮对话是一等公民 | 独立的「上下文改写」环节 + 会话状态机，而不是把历史消息简单拼进 prompt |
| 服务端强制安全 | 只读取数、白名单、行级权限注入、LIMIT 强注入；前端任何勾选仅作为意图提示 |
| 配置驱动 | 模型、提示词、语义层、应用开关全部落库可配，新增指标不改代码 |
| 可降级 | LLM 不可用时降级模型；SQL 失败自愈重试；仍失败则展示推理逻辑与原因 |

### 1.3 问数主链路

```
POST /api/chat/completions (SSE)
  → AuthMiddleware(JWT) → PermissionGuard(ai:qa)
  → ChatService.create_user_message()
  → AgentRuntime.run(session, question, enabled_sources)
      ├─ ① ContextRewriter   多轮改写 + 指代消解（规则优先 + 轻量LLM兜底）
      ├─ ② IntentClassifier  查询/对比/排名/趋势/占比/归因/预警/二次加工/闲聊/越界
      ├─ ③ Planner           生成执行计划（子问题拆分 / 数据源 / 图表类型）
      ├─ ④ SchemaRetriever   语义层 + 向量检索 Top-K 指标/维度/规则/Few-shot
      ├─ ⑤ SQLGenerator      Text2SQL（few-shot + 口径约束 + 权限约束）
      ├─ ⑥ SQLValidator      安全/语法/白名单/LIMIT/权限注入/成本估算
      ├─ ⑦ SQLExecutor       只读连接执行（超时 15s / 行数上限 5000）
      ├─ ⑧ SelfChecker       空结果/报错/异常 → 修正重试（≤2 次）
      ├─ ⑨ ChartAdvisor      依据结果形状推荐图表（确定性规则）
      └─ ⑩ AnswerComposer    流式生成结论文本 + 追问建议
  → SSE 事件流（step / token / table / chart / sql / followups / done / error）
  → ChatService.persist()（消息、SQL、耗时、token、trace_id）
```

### 2.2 后端

| 类别 | 选型 | 理由 |
| --- | --- | --- |
| 语言 | Python 3.11 | 需求硬约束；AI 生态最完善 |

| 部署 | Docker Compose（开发/演示）/ K8s（生产） | — |

### 2.3 模型策略

| 用途 | 默认 | 备选 | 说明 |
| --- | --- | --- | --- |
| 主推理（意图/计划/结论） | DeepSeek-V3 / Qwen2.5-72B | GPT-4o、Claude 3.5 Sonnet、GLM-4-Plus、Moonshot-v1 | 后台「模型配置」可切换 |
| SQL 生成 | 同主推理（可独立配置） | — | temperature=0，确定性输出 |
| 轻量改写（指代消解/摘要） | Qwen2.5-7B / GLM-4-Flash | 规则兜底 | 低延迟、低成本 |
| Embedding | bge-m3 | text-embedding-3-small | 语义检索 |
| 本地兜底 | Ollama + Qwen2.5:7b | — | 断网/配额耗尽时降级 |

统一 `LLMProvider` 抽象（OpenAI 兼容协议优先），模型配置落库 `sys_model`，API Key 用 AES-GCM 加密存储、接口返回脱敏。

```sql
CREATE VIEW bi.v_overall_achieve AS
SELECT g.year, g.unit_code, u.unit_name, u.region, u.is_key_unit,
       SUM(g.biz_goal)                 AS biz_goal,
       SUM(g.solution_goal)            AS solution_goal,
       COALESCE(SUM(c.year_income),0)  AS income,
       COALESCE(SUM(c.year_payment),0) AS payment,
       CASE WHEN SUM(g.biz_goal)>0
            THEN ROUND(SUM(c.year_income)/SUM(g.biz_goal)*100,2) END AS achieve_rate,
       CASE WHEN SUM(g.solution_goal)>0
            THEN ROUND(SUM(c.year_income)/SUM(g.solution_goal)*100,2) END AS solution_rate,
       CASE WHEN COALESCE(SUM(c.year_income),0) < SUM(g.biz_goal)*0.6
            THEN TRUE ELSE FALSE END AS is_warning
FROM bi.fact_goal g
JOIN bi.dim_unit u ON u.unit_code = g.unit_code
LEFT JOIN bi.fact_contract c ON c.unit_code = g.unit_code AND c.year = g.year
WHERE g.month = 0
GROUP BY g.year, g.unit_code, u.unit_name, u.region, u.is_key_unit;
```

### 3.6 数据权限注入机制

在 **SQLValidator** 阶段用 `sqlglot` 解析 AST 后统一注入：

1. 用户可见经营单元 = 其所有角色在 `sys_role_data_perm`（`perm_type='view'`）的 `unit_codes` **并集**；空集 = 不限制；
2. 若目标表/视图存在 `unit_code` 列且用户受限：
   - 有 `WHERE` → `AND unit_code IN (...)`；
   - 无 `WHERE` → 新增 `WHERE unit_code IN (...)`；
   - 含聚合子查询 → 外层包裹 `SELECT * FROM (原SQL) t WHERE t.unit_code IN (...)`（生成 SQL 时强制保留 `unit_code` 列）；
3. 注入后写回 `chat_message.payload.sql`（用户可见的 SQL 即真实执行的 SQL，避免"看到的和跑的不一致"）；
4. 回答中追加提示：「已按您的数据权限范围（N 个经营单元）过滤」。

## 4. 智能问数 Agent 设计（核心）

### 4.1 为什么不用「一把梭 prompt」

| 方案 | 问题 |
| --- | --- |
| 直接把 60 列宽表 DDL 丢给 LLM | 上下文爆炸、幻觉列名、口径不一致、无法解释 |
| 纯 RAG 检索表结构 | 召回不稳定，缺少业务口径 |
| **语义层 + 受控生成（本方案）** | 检索范围受控（只给 Top-K 相关指标/维度）、口径写死在元数据、SQL 可校验、过程天然可解释 |

### 4.2 Agent 状态机

### 4.3 各节点设计

#### ① ContextRewriter（多轮改写）

**目标**：把「那北京呢？」「同比呢？」「只看政企」改写为可独立执行的完整问题。
**输入**：最近 N 轮（默认 6 轮）压缩历史（问题 + 槽位 + 上一轮 SQL 摘要 + 结果预览）+ 当前问题。
**输出**：`{rewritten_query, resolved_slots, need_clarify, clarify_options[]}`。

**策略（规则优先，LLM 兜底，保证低延迟）**：
- 规则层识别三类信号：
  - 指代词：「那/它/这个/上面/再/还/其他/其余」
  - 时间词：「今年/去年/上季度/近 6 个月/YTD/同比/环比」
  - 条件词：「只/仅/排除/剔除/大于/小于/之间」
- 历史中存在「活动主体」（经营单元/行业/产品/时间）且当前问题缺主体 → 继承；
- 时间词 → 用 `sem_rule(scene='time')` 映射为具体区间（「今年」→ `year=2026`）；
- 规则无法判定（多主体歧义）→ 调轻量 LLM，temperature=0，只输出 JSON；
- 仍无法确定 → `need_clarify=true` + 2~3 个候选，前端渲染澄清卡片。

**槽位结构（Slots）**
```json
{
  "metrics": ["biz_income"],
  "dimensions": ["unit"],
  "filters": [{"dim":"industry_cat","op":"=","value":"政企"}],
  "time_range": {"type":"year","value":2026},
  "compare": "yoy",
  "order": {"metric":"biz_income","dir":"desc"},
  "limit": 5,
  "chart_hint": "bar"
}
```

#### ② IntentClassifier

| 意图 | 说明 | 处理策略 |
| --- | --- | --- |
| `data_query` | 常规取数/聚合 | 走完整链路 |
| `compare` | 对比（A vs B、目标 vs 实际） | 计划中生成双指标 |
| `ranking` | 排名（TOP/BOTTOM） | 强制 ORDER BY + LIMIT |
| `trend` | 趋势（月度/季度） | 强制时间维度 + 折线图 |
| `proportion` | 占比 | 计算百分比 + 饼图/环形图 |
| `attribution` | 归因（为什么没完成） | 拆解为多子问题（目标/收入/缺口/同比） |
| `warning` | 预警/风险（高风险项目、低达成） | 走 `v_key_unit` 或 `risk_level` 过滤 |
| `result_ops` | 结果二次加工（排序/改图/导出/翻页） | 复用上轮结果集，**不重跑 SQL** |
| `chitchat` / `out_of_scope` | 闲聊 / 越界 | 模板回复 + 引导回经营数据域 |

实现：轻量模型 + few-shot 分类，temperature=0，输出 JSON；置信度 < 0.6 时降级为 `data_query`。

#### ③ SchemaRetriever（受数据源勾选约束）

1. **过滤**：只保留会话勾选的 `sem_data_source`（默认全选）；
2. **关键词匹配**：中文分词后用 `aliases` 命中指标/维度；
3. **向量召回**：`embedding(question)` 与 `sem_metric/dimension/fewshot.embedding` 余弦相似度 Top-K（K=8），与关键词结果合并去重；
4. **规则注入**：按 `scene` 取全部 `sem_rule`（time/caliber/ranking/chart）；
5. **输出**：精简 Schema 描述，**只给相关表的相关列**，控制在 2k token 内。

精简 Schema 描述示例（喂给 LLM 的形态）：
```
[数据源] 商业市场台账 (bi.fact_contract) — 合同/收入/回款明细，2025-01~2026-12
可用指标:
  biz_income   商业收入 | 别名:收入,营收,签约额 | SUM(f.amount) | 单位:万元 | 口径:不含税签约额
  biz_payment  商业回款 | SUM(f.year_payment)   | 单位:万元
可用维度:
  unit         经营单元 | f.unit_code | 展示: JOIN bi.dim_unit d ON d.unit_code=f.unit_code → d.unit_name
               取值: 北京代表处(BJ), 上海代表处(SH), 浙江代表处(ZJ), ...
  industry_cat 行业大类 | i.industry_cat | JOIN bi.dim_industry i ON i.industry_code=f.industry_code
               取值: 政企, 运营商, 商业市场, 渠道部
  land_date    落地时间 | f.land_date | 类型: date
强制规则:
  - 必须带时间过滤，未指定时默认 year=2026
  - 完成率 = 收入 / 目标 * 100，除数为 0 返回 NULL
  - 未指定 LIMIT 时：排名类取 10，其他取 1000；结果最多 5000 行
  - 输出 JSON：{thought, data_source_ids, sql, chart, confidence}
```

#### ④ SQLGenerator

- 模型：主推理模型，**temperature=0**，强制 JSON 输出；
- 输入：精简 Schema + 改写后问题 + 槽位 + Few-shot（向量召回 Top-3，`verified=true` 优先）+ 上轮 SQL（多轮时）+ 数据权限说明；
- 输出：
```json
{
  "thought": "用户要 2026 年各经营单元商业收入 TOP5：按 unit 分组聚合 biz_income，降序取 5",
  "data_source_ids": [1],
  "sql": "SELECT d.unit_name AS 经营单元, SUM(f.amount) AS 商业收入 FROM bi.fact_contract f JOIN bi.dim_unit d ON d.unit_code=f.unit_code WHERE f.year=2026 GROUP BY d.unit_name ORDER BY 商业收入 DESC LIMIT 5",
  "chart": {"type":"bar","x":"经营单元","y":"商业收入"},
  "confidence": 0.92
}
```
- Few-shot 初始化 20 条（覆盖排名/趋势/占比/对比/同比/预警/筛选），运行期持续沉淀人工校验通过的样本。

#### ⑤ SQLValidator（安全闸门）

用 `sqlglot` 解析后逐项校验，任一不过直接拒绝并记审计日志：

| 校验项 | 规则 |
| --- | --- |
| 语句类型 | 仅允许 `SELECT`（含 CTE）；禁止 INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/GRANT/COPY |
| 多语句 | 含 `;` 分隔的多条语句 → 拒绝 |
| 表白名单 | 所有表必须在 `sem_data_source.object_name` 内 |
| 列白名单 | 列必须属于命中表的注册列 |
| 系统表 | 拒绝 `pg_catalog` / `information_schema` |
| 危险函数 | 禁止 `pg_sleep` / `pg_read_file` / `dblink` / `lo_*` |
| LIMIT | 无 LIMIT 时自动注入（排名类 10，其他 1000） |
| 权限注入 | 追加 `unit_code IN (...)`（§3.6） |
| 复杂度 | 预估扫描量超阈值 → 加严时间过滤并告警 |

#### ⑥ SQLExecutor

- 独立**只读账号**（`bi_readonly`），连接串与主库隔离；
- `SET statement_timeout = 15s`；`SET default_transaction_read_only = on`；
- 结果行数上限 5000，超出截断并提示；
- Decimal→float、Date→str，统一 JSON 化；
- 结果缓存：SQL 归一化后 MD5，Redis 缓存 5 分钟（重复追问立竿见影）。

#### ⑦ SelfChecker（自愈）

| 失败类型 | 处理 |
| --- | --- |
| 语法/语义错误 | DB 错误信息 + 原 SQL 回灌 LLM 修正，重试 ≤ 2 次，SSE 推送「正在重试第 N/2 次」 |
| 空结果 | 放宽过严过滤重试 1 次；仍空则明确回复「该条件下无数据」并给出放宽建议 |
| 结果异常（全 NULL / 溢出） | 提示数据质量问题，展示 SQL 供人工核查 |
| 校验被拒 | 直接返回安全提示，不重试 |
| 超过重试次数 | 降级：展示「推理逻辑 + SQL + 失败原因」，引导用户重述 |

#### ⑧ ChartAdvisor（确定性规则，不消耗 LLM）

| 条件 | 图表 |
| --- | --- |
| 含时间维度且 ≥3 个点 | 折线图 |
| 占比类 / 类别 ≤6 且总和有意义 | 饼图 / 环形图 |
| 排名类（ORDER BY + LIMIT） | 横向条形图 |
| 双指标对比（目标 vs 实际） | 分组柱状图 + 完成率折线（双轴） |
| 类别 >6 且非时间 | 柱状图（可滚动） |
| 单值 | 指标卡 |

#### ⑨ AnswerComposer（流式）

- 输入：结果集预览（前 200 行）+ **程序计算的统计摘要**（最大/最小/均值/合计/占比/TOP1）+ SQL + 意图；
- 关键：**数值由代码算好后注入 prompt，模型只做「表述」不做「计算」**，杜绝 LLM 心算错误；
- 输出：Markdown 结论（3~5 句，含关键数值、极值、与目标差距、同比环比）+ 3 条追问建议；
- SSE 逐 token 推送。

### 4.4 5 步可解释链路的落地（对齐 Demo）

| 步骤 | 真实数据来源 | SSE 事件 |
| --- | --- | --- |
| ① 选择数据表 & 数据时效 | `data_source_ids` → 数据源名称 + `MAX(land_date)` + `sem_rule.caliber` | `step` |
| ② 推理逻辑 | `thought` + 槽位（筛选条件/指标换算） | `step` |
| ③ 执行取数 SQL | 校验后的最终 SQL（含权限注入） | `step` + `sql` |
| ④ 展示取数结果 | 结果行数 + 关键指标 + 环比说明 | `step` + `table` + `chart` |
| ⑤ 执行结束 | 总耗时 / token / 模型 | `step`(done) |

前端收到 `step` 事件更新节点状态（pending → running → done），视觉与 Demo 的 `renderAaSteps()` 完全一致，但数据 100% 真实。

### 4.6 Prompt 工程要点

| 技巧 | 做法 |
| --- | --- |
| 角色与边界 | 「你是经管之星的问数助手，只回答经营数据域问题，其他问题礼貌拒答」 |
| 结构化输出 | 强制 JSON Schema（Pydantic → `response_format` / function call） |

### 4.7 多轮对话的状态管理

```python
@dataclass
class SessionContext:
    session_id: int
    history: list[Turn]              # 最近 6 轮（role/question/slots/sql_summary/result_preview）
    summary: str | None              # 超出 6 轮后的压缩摘要
    active_slots: Slots              # 当前生效槽位（主体/时间/过滤/排序/限量）
    last_result_ref: ResultRef | None  # 上轮结果集引用（用于"排序/改图/导出"）
    source_ids: list[int]
```

- 每轮结束更新 `active_slots`，下一轮复用；
- 超过 6 轮时用轻量模型生成摘要（保留主体、指标、时间、关键结论数值）；
- `result_ops` 意图直接操作 Redis 缓存的结果集（TTL 30min），不重跑 SQL，秒级响应；
- 切换/新建会话清空 `active_slots`。

### 4.8 准确率提升的工程手段

1. **语义层强约束**：LLM 只能使用注册过的指标/维度表达式；
2. **Few-shot 动态召回**：按相似度取 3 条，比固定示例更贴题；
3. **自愈重试**：实测可把一次执行成功率从 ~80% 提升到 ~93%；
4. **校验前置**：语法校验本地完成，不浪费一次真实执行；
5. **反馈闭环**：用户点「数据有误」→ `qa_feedback` → 人工修正 SQL → 入库为 `verified=true` 的 Few-shot，系统持续变准；
6. **评测集**：内置 100 条问答对（覆盖 9 类意图），CI 中运行 Text2SQL 回归（执行结果集比对），低于阈值阻断发布。

### 5.4 关键实现要点

**SSE 与 Celery 的取舍**：问数走 SSE 直连（`StreamingResponse`），不进 Celery，减少延迟；只有导入/导出/造数进 Celery。

```python
@router.post("/completions")
async def completions(req: CompletionReq,
                      user=Depends(current_user),
                      _=Depends(require_perm("ai:qa"))):
    return StreamingResponse(
        chat_service.stream_answer(req, user),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache",
                 "X-Accel-Buffering": "no"},   # 关键：关闭 Nginx 缓冲
    )
```

- **限流**：Redis 令牌桶，单用户 10 次/分钟问数、全局 200 QPS；超限返回 429 + SSE `error` 事件。
- **会话锁**：同一 `session_id` 并发提问用 Redis 锁互斥，避免上下文错乱。
- **审计**：中间件统一记录 `sys_oper_log`（写操作与登录）；问数明细记 `chat_query_trace`。

## 7. 认证与权限设计

### 7.1 认证

| 项 | 方案 |
| --- | --- |
| Token | JWT（HS256）；access 30min（含 `uid/roles/perms_version`），refresh 7d |
| 存储 | access 存 `sessionStorage`，refresh 存 `localStorage`（或 httpOnly Cookie，视部署形态） |
| 无感刷新 | Axios 响应拦截器捕获 401 → refresh 换新 → 重放原请求；并发请求排队，只刷新一次 |
| 登出 | refresh token 入 Redis 黑名单（TTL=剩余有效期），前端清状态 |
| 密码 | bcrypt(cost=12)；初始密码 `123456` + `pwd_must_change=true` 强制改密 |
| 验证码 | 图形验证码 + Redis 校验；失败 3 次后强制要求 |
| 锁定 | Redis `login:fail:{username}`，5 次锁 10 分钟 |

### 7.2 授权（RBAC + 数据权限）

```
用户 ──< 用户角色 >── 角色 ──< 角色菜单(含 ops) >── 菜单
                        └──< 角色数据权限(按菜单 × view/operate/delete × unit_codes[]) >
```

```python
def require_perm(code: str):
    async def dep(user: User = Depends(current_user)):
        if user.is_superadmin:
            return user
        if code not in user.perms:          # perms 登录时加载并缓存到 Redis
            raise ForbiddenError(f"缺少权限：{code}")
        return user
    return dep
```

**数据权限注入**见 §3.6：在 `SQLValidator` 中统一注入，覆盖「智能问数 / 台账查看 / 报表」，一处实现全局生效。

**权限缓存与失效**：`perms:{user_id}` 存 Redis（TTL 30min）；管理员改角色权限时批量删除相关用户缓存并提升 `perms_version`，使旧 access token 失效。

| 方案 | 说明 | 适用 |

## 9. 造数方案（Data Factory）

### 9.1 设计原则

- **可复现**：`random.seed(20260830)`，同版本脚本产出完全一致的数据；
- **业务合理**：不是纯随机噪声，而是「带分布的模拟」，让分析结果讲得通；
- **可分析**：刻意制造分析素材（高/低达成单元、高风险项目、同比涨跌、季节性波动）。

### 9.2 生成策略

```
├── gen_contracts.py     # fact_contract：围绕目标反推收入 → 生成合同明细
├── gen_ppl.py           # fact_ppl：机会点管线（阶段/风险/预计落地）
├── gen_system_data.py   # 用户/角色/菜单/权限/快捷问题/预置会话/反馈/操作日志
├── build_views.py       # 建视图 + 索引 + ANALYZE
└── main.py              # python -m scripts.data_factory.main --scale 1.0
```

**关键算法（让数据"讲得通"）**

1. **单元体量分层**：按 `region` 给每个单元分配 `size_factor ∈ [0.4, 2.0]`（华北/华东大，西部小）；
2. **目标生成**：`年目标 = 8000 × size_factor × (1 + growth)`，月度按季节权重分配（Q4 权重 0.32，Q1 权重 0.18）；
3. **收入生成（关键）**：
   - 每单元每年完成率 `r ~ Normal(μ=0.85, σ=0.15)`，clamp 到 [0.35, 1.25]；
   - 刻意指定 2 个单元为「低达成预警」（r≈0.5）、1 个为「超额达成」（r≈1.18）；
   - `年收入 = 年目标 × r`；
4. **合同拆分**：年收入拆成 N 条合同（N ~ Poisson(λ=25)），单笔金额服从**对数正态**（长尾：少数大单），并做整数化 + 尾差调整，保证 `Σ合同 = 年收入`（误差 < 0.01）；
5. **月度/季度分摊**：按落地月份摊入 `m1..m12`，季度自动汇总（保证 `q1 = m1+m2+m3`）；
6. **回款**：`回款 = 收入 × pay_ratio`，`pay_ratio ~ Beta(6,2)`（多数 0.7~0.95），回款月份滞后收入 1~3 个月；
7. **2025 vs 2026**：2026 整体比 2025 增长 12%，但个别单元下滑（制造同比负增长案例）；
8. **风险与阶段**：`risk_level` 按「金额越大、落地时间越远 → 风险越高」的概率生成，高风险占比约 12%；
9. **行业/产品结构差异**：如「智能制造」2026 同比增长 +35%，制造结构性热点素材。

**生成后一致性校验（自动跑）**
```python
assert abs(sum(contract.year_income) - v_overall_achieve.income) < 0.01
assert all(q1 == m1 + m2 + m3 for each row)
assert 0.30 <= overall_achieve_rate <= 1.30
assert 0.08 <= ratio_of(risk_level='高') <= 0.18
```

## 10. 关键流程时序

### 10.1 登录

```
前端 → POST /auth/login {username, password, captcha, captcha_id}
后端 → 验证码校验(Redis) → 失败计数检查 → 查用户 → bcrypt 校验 → 状态/有效期检查
     → 加载角色/菜单/权限/数据权限 → 生成 access + refresh
     → 写 sys_oper_log(login) → 返回 {token, userInfo, menus, perms, dataPerms}
前端 → 存 token → 拉 configStore → 按 menus 渲染侧边栏 → 跳转 /ai-qa
```

### 10.2 问数（SSE 流式）

```
前端 → POST /chat/completions (SSE)
后端 → 建 user message → 获取 SessionContext（Redis 锁）
     → REWRITE   : 规则命中 → 改写为"2026年各经营单元商业收入TOP5"
     → INTENT    : ranking，slots={metrics:[biz_income], dims:[unit], time:2026, limit:5}
     → RETRIEVE  : 语义层 + 向量 → 精简 Schema
     → GENERATE  : LLM → SQL（含 thought / chart 建议）
     → VALIDATE  : sqlglot 白名单校验 + LIMIT 注入 + 数据权限注入
     → EXECUTE   : 只读连接，statement_timeout=15s
     → CHECK     : 成功 → CHART(bar) → COMPOSE（注入统计摘要）
     → 流式推送 step / sql / table / chart / token / followups / done
     → 持久化 chat_message(payload) + chat_query_trace
前端 → 逐步渲染 5 步链路、表格、图表、结论 → 生成追问 chips
```

### 10.3 多轮追问

```
Q2「那北京呢？」
→ REWRITE：检测到指代词 + 历史 active_slots{dims:[unit], time:2026}
        → 改写为"2026年北京代表处的商业收入是多少"
→ INTENT：data_query（filters 新增 unit=北京代表处）
→ 生成新 SQL（WHERE 继承 year=2026 AND unit_code='BJ'）
→ 权限校验：BJ 在用户可见范围内 → 通过；否则返回"无该单元数据权限"
```

### 10.4 反馈闭环

```
用户点「数据有误」→ POST /chat/data-error {message_id, comment}
→ 生成 qa_feedback(status=待处理, 快照 question + ai_reply)
→ 管理员 /feedback/review 看到（橙色"待处理"标签）
→ 打开处理弹窗 → 填备注 → 改状态 → PUT /feedbacks/{id}
→ 列表实时变绿"已处理"；可跳转 /ai-qa?session={id} 回放原会话
```

## 11. 非功能设计

### 11.1 性能

| 目标 | 手段 |
| --- | --- |
| SSE 首字 ≤ 2s | 改写/意图用轻量模型并行；Schema 检索缓存；LLM 流式 |
| 端到端 ≤ 8s | 结果缓存（Redis 5min）；并发执行「检索」与「意图分类」 |
| 大结果渲染 | 表格虚拟滚动；图表数据下采样（>500 点聚合） |
| 数据库 | 覆盖索引；`v_*` 视图按需物化（`REFRESH MATERIALIZED VIEW` 每日调度） |
| 前端首屏 | 路由级代码分割；AntD 按需引入；Gzip/Brotli |

### 11.2 安全

| 威胁 | 防护 |
| --- | --- |
| SQL 注入 / 越权取数 | 语义层受控生成 + sqlglot 校验 + 表/列白名单 + 只读账号 |
| 越权访问他人数据 | 行级数据权限注入（服务端强制）+ 接口级鉴权 |
| 暴力破解 | 验证码 + 失败锁定 + 限流 |
| XSS | 前端默认转义；Markdown 渲染禁用裸 HTML（`rehype-sanitize`） |
| CSRF | SameSite Cookie + 自定义头校验 |
| 密钥泄露 | API Key AES-GCM 加密落库；接口返回 `sk-***abcd` 脱敏；不进日志 |
| 提示词注入 | 用户问题与系统提示分离；对可疑指令（"忽略以上指令"）做规则拦截 |
| 越权下载 | 导出走服务端鉴权 + 预签名 URL（TTL 5min） |

### 11.3 可观测

- **链路**：每问数生成 `trace_id`，贯穿 10 个节点，落 `chat_query_trace`；OTel 导出到 Jaeger；
- **指标**：问数成功率、SQL 一次通过率、各节点 P50/P95 耗时、token 消耗、反馈率、DAU → Prometheus + Grafana；
- **日志**：结构化 JSON（trace_id/user_id/level/msg），Loki 收集；禁止记录密码与 API Key；
- **告警**：LLM 连续失败 > 5 次、SQL 失败率 > 20%、P95 耗时 > 20s → 企微/邮件告警。

### 11.4 可靠性与降级

| 场景 | 降级策略 |
| --- | --- |
| 主 LLM 不可用 | 自动切换到 `fallback_models` 链（DeepSeek → Qwen → 本地 Ollama） |
| LLM 超时 | 重试 2 次（退避 1s/3s）；仍失败提示「模型繁忙，请稍后重试」 |
| SQL 执行失败 | 自愈重试 ≤2 次；仍失败展示推理逻辑 + SQL + 原因 |
| Redis 不可用 | 降级为进程内缓存，限流改为本地令牌桶（功能不中断） |
| 大结果集 | 截断到 5000 行并提示「结果过大，建议增加筛选条件」 |

## 14. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
| --- | --- | --- | --- |
| Text2SQL 准确率不达标 | 核心体验 | 中 | 语义层强约束 + Few-shot 召回 + 自愈重试 + 反馈闭环；预留人工 Few-shot 运营后台 |
| 中文时间/口径理解偏差 | 数据错误 | 中 | `sem_rule` 显式规则 + 评测集覆盖时间类 30% |
| LLM 成本高 / 限流 | 预算 | 中 | 轻量模型处理改写；结果缓存；token 监控与告警；本地 Ollama 兜底 |
| 多轮上下文丢失 | 体验 | 中 | 槽位显式建模 + 摘要压缩 + 多轮评测用例 |
| 数据权限注入破坏 SQL | 功能/安全 | 中 | sqlglot AST 注入 + 单测覆盖（聚合/CTE/子查询/无 WHERE 四类） |
| 造数不真实导致演示效果差 | 演示 | 低 | 完成率分布建模 + 一致性校验 + 人工抽检 20 条 |
| 语音能力浏览器兼容差 | 可选功能 | 中 | 默认关闭；Web Speech 优先、服务端兜底；不可用时隐藏入口 |
| 进度风险（Agent 调试耗时） | 交付 | 中 | 迭代 2 就打通最小闭环，后续迭代持续调优而非最后集中攻关 |
