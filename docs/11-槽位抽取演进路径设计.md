> 本文是 `docs/10-槽位Slots机制详解.md` 的续篇。上篇讲「现状是什么」，本篇讲「怎么演进、分几步、每步的验收标准」。
>
> 相关代码：`server/app/agent/slots.py`、`server/app/agent/nodes/rewrite.py`、**`server/app/agent/nodes/slot_llm.py`（阶段 1 新增）**

## 0. 结论先行

| 阶段 | 内容 | 状态 | 预估 |
| --- | --- | --- | --- |
| **阶段 0** | 修规则层的确定性缺陷 | ✅ **已完成** | — |
| **阶段 1** | 规则优先 + LLM 兜底 | ✅ **已完成** | — |
| **阶段 2** | 引入向量召回层 | 待做 | 3~5 天 |
| **阶段 3** | 查询规约 + SQL 编译器 | 待做（重构级） | 2~3 周 |

阶段 0 与阶段 1 是**互补**关系，不是替代：阶段 1 让有模型时结果更好，阶段 0 让**没有模型时**（降级模式、离线演示、无 Key 环境）不会给出反向或自相矛盾的条件。

**核心判断：现有方案的错误不在于「用了规则」，而在于用同一套字面匹配处理了两类性质不同的字段。** 演进的关键是**分治**：

| 类别 | 字段 | 词表 | 机制 |
| --- | --- | --- | --- |
| **闭集槽位** | `time_range`、`compare`、`order`、`limit` | 有限可枚举 | **正则 —— 保持不动** |
| **开集槽位** | `metrics`、`dimensions`、`filters`/`subject` | 无界，随业务增长 | 语义匹配 + LLM 兜底 |

闭集字段用正则更快、更省、更确定，换成模型是退化；开集字段用字面匹配必然有覆盖盲区。

## 2. 阶段 1（已完成）：规则优先 + LLM 兜底

### 2.1 为什么这是第一步

`rewrite()` 早就预留了入口，参数传进来了却从未使用：

```python
async def rewrite(
    question: str,
    prev_slots: Slots,
    schema: SchemaContext,
    *,
    default_year: int = 2026,
    providers: Optional[list] = None,   # ← 传进来了，函数体从未使用
    history: str = "",                   # ← 同上
) -> RewriteResult:
```

而技术方案 §4.2 白纸黑字写的就是：

```632:639:docs/02-技术方案.md
**策略（规则优先，LLM 兜底，保证低延迟）**：
- 规则层识别三类信号：
...
- 规则无法判定（多主体歧义）→ 调轻量 LLM，temperature=0，只输出 JSON；
```

**所以这一步不是引入新方案，而是把已经设计好、参数都传了却没写的那部分补完。**

### 2.2 实现结构

新增 `server/app/agent/nodes/slot_llm.py`，四个职责：

```
assess(question, slots, schema)  →  ExtractionAssessment
    │                                 · confidence  置信度
    │                                 · issues      可疑信号描述
    │                                 · suspicious  允许被 LLM 覆盖的字段集合
    ▼
needs_llm() ?──否──▶ 直接用规则结果（零额外开销）
    │是
    ▼
extract_slots_llm(...)  →  Optional[Slots]
    │   · 只挑 is_remote 的 Provider（TemplateProvider 只产 SQL，不填槽位）
    │   · asyncio.wait_for 硬超时
    │   · 失败 / 非 JSON / 校验后为空 → 一律返回 None
    ▼
validate(payload, schema)  →  Optional[Slots]
    │   ★ 安全核心：过语义层白名单，编造的 code 与取值全部丢弃
    ▼
combine(rule, llm, suspicious)  →  Slots
```

### 2.3 三条硬约束（决定了这层不会把系统搞坏）

**① 规则结果优先。** LLM 只补两类地方：规则没抽到的**空位**，以及被判定为**可疑**的字段。其余字段即使模型给不同答案也沿用规则——规则是字面命中，不存在幻觉，让模型去改一个已经正确的结果只会引入不确定性。

```python
def pick(name: str, rule_val: Any, llm_val: Any) -> Any:
    if name in suspicious and _filled(llm_val):
        return llm_val
    return rule_val if _filled(rule_val) else llm_val
```

**② 输出必须过语义层白名单。** 模型只能在语义层已有的 code 与取值里做选择，拿不到「发明指标」的能力：

```python
def validate(payload: dict, schema: SchemaContext) -> Optional[Slots]:
    """按语义层白名单校验模型输出，剔除编造内容。

    这是本模块的安全核心：**模型只能在语义层已有的 code 与取值里做选择**。
    校验后无任何有效字段返回 None，等价于「模型没帮上忙」。
    """
```

校验项：指标 code、维度 code、filter 的 dim 与 op、取值是否在 `value_map` 内、subject 是否已知、年度合理区间、order.by 是否为已知指标、limit 上限。

**③ 失败静默回落。** 未开启 / 无远程模型 / 超时 / 解析失败 / 校验后为空 → 返回 `None`，行为与改造前完全一致。`settings.SLOT_LLM_ENABLED = False` 即可整体关闭。

### 2.4 置信度与可疑信号

```python
_WEIGHTS = {"metrics": 0.45, "dimensions": 0.25, "subject": 0.20, "filters": 0.10}
```

权重体现「指标最重要——它决定查什么数」。`time_range` 等闭集字段**不参与**打分，因为置信度回答的是「我们知不知道要算什么」，而不是「有没有识别到时间」。

四类可疑信号（命中即标记对应字段为 suspicious，允许 LLM 覆盖）：

| 信号 | 正则 | 影响字段 | 置信度系数 |
| --- | --- | --- | --- |
| 否定 | `不含\|不包含\|除了\|排除\|剔除\|不算\|不要\|不是\|非(?!常\|凡\|法)` | filters, subject | ×0.5 |
| 区间/比较 | `\d+\s*(?:万\|亿)?\s*(?:到\|至\|~\|-)\s*\d+` 等 | filters | ×0.6 |
| 取值歧义 | 同取值命中多个维度 | filters, subject | ×0.6 |
| 同维度多值 | 同 dim 出现多条筛选 | filters | ×0.7 |

歧义与多值都从 `slots.filters` 反推，不需要重新匹配文本——这是显式槽位带来的便利。

### 2.5 配置

```python
SLOT_LLM_ENABLED: bool = True        # 总开关，关闭即退化为纯规则
SLOT_LLM_THRESHOLD: float = 0.6      # 调高→更少调用；调低→更多覆盖
SLOT_LLM_TIMEOUT_MS: int = 3000      # 主链路串行执行，必须设上限
SLOT_LLM_MAX_TOKENS: int = 1024
```

### 2.6 验收

`tests/test_slot_llm.py` 共 25 + 8 = 33 个用例，全量 105 passed。关键用例：

- `test_rewrite_without_providers_keeps_old_behaviour` —— 无模型时行为与改造前一致（**回归保护**）
- `test_extract_slots_llm_disabled` —— 关闭开关即纯规则
- `test_validate_drops_unknown_metric_and_dimension` —— 幻觉被白名单拦截
- `test_rewrite_llm_fixes_reversed_negation` —— 「不含政企」从 `=` 纠正为 `!=`
- `test_rewrite_uses_llm_when_rules_fail` —— 「今年卖得怎么样」不再只能澄清

### 2.7 已知代价

1. **主链路延迟**：命中兜底时 +300~800ms，受 `SLOT_LLM_TIMEOUT_MS` 封顶。
2. **成本**：每个兜底请求一次轻量模型调用（约数百 token）。
3. **非确定性**：`temperature=0` 已尽量收敛，但仍无法做到规则层那样逐字可复现。
4. **当前用的是主模型**（deepseek-chat），不是「轻量模型」。若后续接入小模型（如 qwen2.5:7b 本地），应在 `extract_slots_llm` 里优先挑选成本最低的 Provider 而非第一个。

### 2.8 实测：A/B 对照结果

改造前（`git stash` 回退后重启）与改造后各跑一次 100 条评测**同机、同模型、同数据**对照。

| 口径 | 用例数 | 改造前 | 改造后 | 差值 |
| --- | --- | --- | --- | --- |
| 共同用例（原始） | 85 | 72 (85%) | 79 (93%) | +7 |
| **剔除配额超时后** | **78** | **72 (92%)** | **72 (92%)** | **0** |
| ├ 兜底作用面 | 24 | 23 (96%) | 24 (100%) | +1 |
| └ 对照组（不触发兜底） | 54 | 49 (91%) | 48 (89%) | −1 |

**结论：在可比的 78 条上净变化为 0 —— 既未回归，也未显著提升。**

逐条看只有 4 条翻转：
- `#42 完成率低于60%的预警单元` 前✗→后✓，**触发兜底**，可归因于本次改动；
- `#62` 后✓ 但仅 35ms（缓存命中），不算真实改进；
- `#7` `#44` 前✓→后✗，**均不触发兜底**，属模型输出随机性，与改动无因果关系。

### 2.9 这次测量暴露的三个问题

**① 模型配额耗尽（与 `docs/06` 同源）。** 改造前那轮跑到 #73 后出现 7 条 300s 超时，日志明确记录 `quota exhausted`。这是环境问题，不是准确率的真实反映。

**② 缓存命中不对称——污染了对照。** 改造后 26 条在 500ms 内返回（物理上不可能是真实调用），改造前 0 条。根因：`.env` 里 `QA_CACHE_TTL=3600` 覆盖了代码默认的 300，缓存实际存活 1 小时，前一轮运行与手动探测给后一轮"播种"了。
→ **评测前必须清缓存，且应把 TTL 调回短值或给评测加专用开关。**

**③ 兜底超时过短（已修）。** 日志统计：兜底触发 61 次，成功 44 次，失败 17 次——其中 **9 次是 3000ms 超时**（约 15%），7 次被白名单拒绝（安全网正常工作），1 次返回非 JSON。
主链路 SQL 生成 P90 约 13s，3s 预算根本不够。已将 `SLOT_LLM_TIMEOUT_MS` 调整为 8000。

### 2.10 评测集对这类改动没有分辨力

| 修复项 | 评测集覆盖 | 判据 |
| --- | --- | --- |
| 否定识别 | **0 条** | 无 |
| 取值歧义 | 1 条（#60） | 仅 `min_rows: 1`，按 unit 还是 industry_cat 过滤都能过 |
| 同维度多值 | 5 条 | 仅 `min_rows`/`max_rows`，无法区分筛选条件对错 |
| 多轮槽位 | **0 条**（100 条全是单轮） | 无 |

更根本的一点：**强模型下槽位错误的边际影响很小**。实测「不含政企的经营单元收入」——槽位层给的是 `= 政企`（错的），但模型照着问句原文写出了 `<> '政企'`（对的）。槽位真正起作用的地方是：

- **多轮追问**（问句不自足，必须靠槽位补全）—— 评测集完全没覆盖
- **弱模型 / 降级模式** —— 此时 SQL 由 Few-shot 直接给出，槽位不参与
- **澄清判定** —— 只有 `expect_clarify` 类用例覆盖

→ 要验证这类改动，应该跑 `make check-multiturn`（多轮 E2E）而不是 `run_eval`（100 条单轮）；同时评测集需要补充否定、多轮、歧义用例，并加严判据。

### 2.11 配额受限时的分层验证方案

模型配额有限时不该硬跑 `run_eval`（单次约 100 次调用）。按「性价比」分层：

| 层级 | 手段 | LLM 调用 | 能证明什么 |
| --- | --- | --- | --- |
| **L0** | `make check-slots`（黄金快照比对） | **0** | 槽位抽取行为未发生意外变化 |
| **L0** | `pytest tests/`（129 个用例） | **0** | 各修复点与兜底接线的正确性 |
| **L1** | 离线回放 diff（见下） | **0** | 真实语料上到底哪些问句变了、变成了什么 |
| **L2** | 本地 Ollama 跑 `check-multiturn` | 本地，免费 | ⚠️ **本机实测不可行**，见下 |
| **L3** | 云端跑 `run_eval` | ~100 次/轮 | 强模型下的端到端准确率 |

#### L2 实测结论：本机 Ollama 跑不通问数链路（已还原）

环境：Ollama 0.33.2 + `deepseek-r1:14b`（9GB，18 个月前的版本）/ 32GB 内存。

用**真实 Prompt**（2 条消息约 5729 token：23 指标 + 16 维度 + 17 规则 + 3 条 Few-shot）压测：

| 模式 | 耗时 | 结果 |
| --- | --- | --- |
| JSON 模式（8192 / 2048） | **2.9s** | 直接放弃：`{"question":..., "answer":"请提供正确的 SQL 语句。"}` |
| 普通模式（2048） | 86.7s | 写出了 SQL，但**理解错问题**——问「各经营单元收入排名」，答成「各产品线收入同比」 |

小 Prompt（300 token，2 指标 1 维度）时它能正确输出 JSON（12.6s），说明**不是协议/兼容性问题，是模型能力不足以处理真实规模的 Prompt**，且被 Few-shot 示例带偏。

→ 结论：此环境下 L2 不可行，验证应停留在 L0/L1，等配额恢复再走 L3。

**顺带暴露一个设计风险**：`llm/router.complete()` 的语义是「**第一个返回非空内容即采纳**」。
本地模型返回的是非空但完全错误的 JSON，会被正常采纳——**静默产出错误结果，比直接失败更危险**。
因此试验结束后不仅还原了默认模型，还把本地模型显式 `enabled=False`，避免它留在降级链里污染结果。

### 2.12 新模型下的验证结果

按 §2.11 的分层方案做完整验证，**没有跑全量 100 条**（单次约 100 次调用）：
先跑多轮 E2E（5 次调用），再跑离线诊断出的 29 条受影响子集，合计约 60 次调用。

#### ① 多轮 E2E：5/5 全部通过（qwen3.7-max）

这是槽位改动的**主战场**（评测集 100 条全是单轮，测不到）：

| 轮次 | 问句 | 改写结果 |
| --- | --- | --- |
| Q1 | 2026年各经营单元收入排名是多少 | 首轮排名，10 行 |
| Q2 | 那北京呢 | `2026年北京代表处商业收入…` —— 指代消解，继承 2026 + 商业收入 |
| Q3 | 它同比呢 | 主体（北京代表处）保留 + 加入同比 |
| Q4 | 只看政企行业 | `2026年北京代表处行业大类为政企收入同比…` —— **条件叠加** |
| Q5 | 换成饼图 | `result_ops`，17ms，不重跑 SQL |

Q4 的四个条件（2026 年 + 北京代表处 + 政企 + 同比）来自三轮对话，全部正确继承。

#### ② 受影响 29 条子集：29/29 = 100%（qwen3.7-max）

首轮 26/29，3 条失败；定位根因后重跑该 3 条全部通过：

| 用例 | 首轮失败原因 | 定位 |
| --- | --- | --- |
| #56 | 319s 超时 | 基础设施，非准确率 |
| #87 | PostgreSQL 执行报错 | SQL 生成问题，槽位抽取本身正确 |
| #88 | 返回 0 行（走了澄清） | **兜底超时导致**，见下 |

#### ③ 关键发现：兜底被超时阈值大面积卡死

统计发现兜底触发 93 次、成功仅 53 次，**超时 32 次（34%）**。

兜底 Prompt 仅约 1609 token（远小于 SQL 生成的 5729），耗时主要由模型首字延迟决定。
同一个问题、同一个模型的对照给出了干净的因果证据：

```
19:45:59  llm_used=False → 槽位为空 → 澄清   → 0 行  → FAIL
19:55:50  llm_used=True  → metrics=['income_gap', …] → 10 行 → OK
```

兜底补上的正是规则层完全抽不到的指标（「哪些因素导致整体未达成」→ `income_gap` 目标缺口），
**把「无法回答」变成了「给出答案」**——这是阶段 1 最有价值的部分。

#### ④ 换到 qwen3.7-flash 后的阈值标定

换模型后按配置注释要求重新实测（10 条样本）：

| 指标 | 数值 |
| --- | --- |
| 成功 | 10/10 |
| 最小 / P50 / P90 / 最大 | 10.7s / **15.3s** / **18.0s** / 29.7s |
| 均值 | 16.0s |

最终定为 **30000ms**。两条实测依据：

1. **阈值是上限而非固定开销。** 正常调用该多久就多久（15s 就是 15s），
   它只在调用真的拖长时才截断——放宽不会拖慢正常请求，只会放过本可成功的慢调用。
2. **最需要兜底的恰恰是最慢的用例。** 规则层 `confidence=0.0`（一点线索都没给）时
   模型要从全部指标里挑，实测约 30s。卡在 20s 等于精准砍掉兜底价值最高的那一批：
   实测 #88 在 20s 下超时→澄清→0 行，30s 下成功→10 行。

改后统计（7 次触发）：**成功 6 次，超时 0 次**；
6 条受影响用例（#42/#60/#67/#76/#87/#88）**6/6 全部通过**。

> ⚠️ **测量陷阱**：不要用 `readonly_session()` 跑这类测量。
> 只读账号无 `sys_model` 权限（`InsufficientPrivilegeError`），
> `build_providers` 会静默回退到 `.env` 的模型——测出来的不是目标模型。
> 必须用主库会话（`get_db()`，与真实后端一致）。

顺带修了一条误导性日志：模型返回全空槽位时原本报「未通过白名单校验」，
实际是模型没给内容。两者排障方向完全不同（前者是模型能力问题，调阈值无效）。

### 2.13 已实现：输出结构校验 + 用户端如实标注

针对上面的风险做了两件事。

#### ① 输出不合规 == Provider 调用失败

`router.complete()` 新增 `validate` 参数（`(str) -> Optional[str]`，返回原因即失败）：

```python
resp = await complete(..., validate=validate_sql_output)
```

未通过校验的 Provider 被**跳过并继续降级**，而不是被采纳。两个校验器各有分工：

| 校验器 | 判什么 | 失败含义 |
| --- | --- | --- |
| `validate_sql_output` | JSON 可解析 + 有 `sql` 字段 + 以 SELECT/WITH 开头 | 输出**残缺** → 换模型 |
| `validate_slot_output` | JSON 可解析 | 连格式都没遵守 → 换模型 |

**刻意不校验 SQL 是否写对**：语法错、越权、引用不存在的列属于「模型理解了意图但写错了」，
交给 `sql_validate` + 自愈重试（带上报错让**同一个**模型改）比换模型更有效。两种失败语义不同，不能混。

不传 `validate` 时行为与改造前完全一致（首个非空即采纳），已有调用方不受影响。

#### ② 用户端看到「答案是谁给的」

`LLMResponse` 新增 `provider` / `fallback` 字段，链路透传到前端：

```
complete()  →  SQLDraft.fallback  →  RunResult.model_fallback
           →  payload + done 事件  →  chatStore  →  AiAnswerCard
```

前端区分两种状态（视觉上用不同颜色）：

- **降级**（橙）：压根没有可用远程模型，结论是程序化摘要
- **备用模型**（蓝）：有可用模型，但首选的输出未通过校验，实际由备用模型产出

顺带修了一个既有缺口：`done` 事件此前没有把 `degraded` 落进 payload，
导致流式过程中降级提示**根本不显示**，只有刷新页面从库里回放时才可见。

#### 遗留发现：Provider 挂起会让降级链形同虚设

冒烟时复现：云端配额耗尽后，4 个 Provider **串行**各等 60–90s 才失败，
整次请求 200s 仍未落到兜底（测试脚本超时）。此时「降级链」理论存在、实际不可用。

- 这是**既有问题**，非本次引入；本次的 `SLOT_LLM_TIMEOUT_MS` 只保护兜底抽取，主链路 SQL 生成无超时。
- 建议后续给 `complete()` 的每个 Provider 加各自超时（`asyncio.wait_for`），
  并对连续失败的 Provider 做短期熔断；`stream_complete`（结论生成）同样需要处理。

> **已决定暂不处理，记入待办**：详见 `docs/12-技术债与待办备忘录.md` 第 1 项（P0）。
> 阈值取舍需单独评估，不要夹带在其它改动里做。

**关键认识：本次改动 90% 是确定性逻辑**（否定识别、歧义收敛、多值合并），只有兜底那一段依赖模型。所以 L0/L1 就能覆盖绝大部分风险，L3 只在配额充裕时才有必要。

## 3. 阶段 0（已完成）：规则层的确定性缺陷

**为什么阶段 1 之后仍要做阶段 0？** 因为 LLM 兜底只在有可用模型时生效。**一旦模型不可用（降级模式、离线演示、无 Key 环境），这些场景会退回到错误行为。**

| 项 | 状态 | 说明 |
| --- | --- | --- |
| 多值被 merge 覆盖 | ✅ 已修 | `merge` 改为按 `(dim, op)` 分组，`op="in"` 取并集 |
| 否定识别 | ✅ 已修 | 位置规则判定否定词紧邻取值 → `op="!="` |
| 跨维度取值歧义 | ✅ 已修 | 同一取值收敛为单一维度，不再产生矛盾筛选 |

### 3.1 否定识别

采用「**否定词紧邻取值左侧**」的位置规则，只有否定词出现在取值之前且间隔 ≤ 2 字符时才算否定。这样「不含政企、只看北京代表处」里的「北京代表处」不会被误判为排除。

```python
def is_negated(question: str, key: str) -> bool:
    """该取值在问句中是否被否定词修饰（紧邻其左侧）。"""
```

判定生效时输出 `op="!="`，且**该取值不作为分析主体**——「不含北京」问的不是北京。

单字「非」走 `NEGATION_WEAK_RE = re.compile(r"非(?!常|凡|法|洲)")`，避免「非常 / 非凡 / 非法 / 非洲」误伤。

### 3.2 取值歧义收敛

「渠道部」既是经营单元也是行业。修复前会同时加两个筛选 = 查「既是渠道部行业、又是渠道部单元」的数据——**SQL 能跑通、只是结果为空或偏少，是最难察觉的一类错误**。

修复后由 `_resolve_ambiguity` 收敛为一个：主体维度优先（`SUBJECT_DIM_CODES`），其次按语义层维度顺序。

> 这里**不追求猜对**——猜对是 LLM 兜底层的职责（`assess` 仍把歧义标记为 suspicious，让模型来选）。
> 它的价值在于：**没有模型时也不会给出自相矛盾的 SQL**。

由于规则层已收敛，`assess` 的歧义检测相应改为**从问句文本**判定（`_ambiguous_values(question, schema)`），而不是从 `slots.filters` 反推——slots 里已经看不出「这个取值本来也可能指别的维度」了。

### 3.3 验收

新增 21 个用例，全量 **126 passed**。关键回归守卫：

```python
async def test_rewrite_without_llm_still_produces_not_equal():
    """没有可用模型时，规则层也必须给出 != —— 这正是阶段 0 的意义。"""
    r = await rewrite("不含政企的收入", Slots(), SCHEMA, providers=None)
    assert r.used_llm is False
    assert r.current.filters == [{"dim": "industry_cat", "op": "!=", "value": "政企"}]
```

冒烟验证（真实语义层取值）：

| 问句 | 抽取结果 |
| --- | --- |
| 高风险项目有哪些 | `risk_level = 高` |
| 不含高风险的合同金额 | `risk_level != 高` |
| 渠道部的收入 | 单条 `unit = 渠道部`（歧义已收敛） |
| 除了北京代表处之外的经营单元收入 | `unit != 北京代表处` |
| 不含政企、只看北京代表处的收入 | `industry_cat != 政企` + `unit = 北京代表处` |
| 非常多的收入 | 无误判（「非常」已排除） |

## 4. 阶段 2（待做）：向量召回层

### 4.1 动机

阶段 1 能覆盖长尾，但每次都要付一次模型调用的延迟与成本。**大量问法其实是「换个说法」，用向量召回就能解决，无需出动 LLM。**

基础设施已经预留了：

```python
EMBEDDING_MODEL: str = "bge-m3"
EMBEDDING_BASE_URL: str = ""
```

加上 `sem_fewshot.embedding BYTEA` 那个「预留」字段——配置与字段都齐了，只缺一个 embedding 客户端。

### 4.2 做法

1. 对 `sem_metric`（`name + aliases + caliber`）与 `sem_dimension`（`name + aliases`）建向量索引；
2. 对 `value_map` 的取值建索引（取值量小，可全量）；
3. 问句与候选做相似度召回，取 Top-1（指标/维度）或 Top-K（取值）；
4. 索引在建/改语义层时增量更新，或启动时全量重建。

### 4.3 收益与边界

- **收益**：本地模型约 10~30ms，比 LLM 快两个数量级、零 API 成本、结果确定（同输入同输出）。
- **边界**：向量只回答「选哪个」，回答不了「怎么选」。否定、区间、多值、比较**仍需 LLM 或阶段 3**。

所以阶段 2 不是替代阶段 1，而是**在它前面加一层廉价召回**，形成三级：

```
字面命中（0ms，高置信）
   ↓ 未命中
向量召回（~20ms，中置信）
   ↓ 仍拿不准 / 存在可疑信号
LLM 兜底（~500ms，覆盖长尾）
```

### 4.4 验收

- 阶段 1 的 LLM 触发率下降（可在日志里统计 `llm_used=true` 占比）；
- 「营收」「卖了多少」「签了多少」等说法都能归一到 `biz_income`；
- 离线（无 LLM）状态下这些问法依然可用。

## 5. 阶段 3（待做，重构级）：查询规约 + SQL 编译器

### 5.1 思路

**不再让模型写 SQL，而是让它（或规则+向量）输出结构化查询规约，由确定性代码编译成 SQL。**

```
{ metric: biz_income,
  dimensions: [unit],
  filters: [{dim: industry_cat, op: "=", value: "政企"},
            {dim: unit,         op: "in", value: ["北京代表处","上海代表处"]}],
  having: [{metric: biz_income, op: "between", value: [3000, 5000]}],
  time: {year: 2026}, order: {by: biz_income, dir: "desc"}, limit: 10 }
        ↓ 确定性编译器
SELECT d.unit_name, SUM(f.year_income) ...
HAVING SUM(f.year_income) BETWEEN 3000 AND 5000 ...
```

这就是 dbt Semantic Layer / MetricFlow、Cube、Looker LookML 的路子。

### 5.2 收益

- **口径 100% 由代码保证**——不可能再算出「目标被放大 585 倍」那类错误（见 `sem_rule` #7 记录的真实事故）；
- 区间、否定、多值、比较**天然可表达**（这是阶段 1/2 都做不到的）；
- 结果可按规约哈希缓存，复用率高于按问题文本缓存；
- 前端能直接做可视化查询构建器（拖指标、选筛选）。

### 5.3 与本项目契合度：很高

语义层**已经是一个约 70% 完备的 metric layer**：

| Metric Layer 需要 | 本项目现状 |
| --- | --- |
| 指标定义（表达式 + 单位 + 聚合方式） | ✅ `sem_metric.expr_sql` / `unit` / `agg_default` |
| 维度定义（表达式 + 展示列 + JOIN） | ✅ `sem_dimension.expr_sql` / `display_expr` / `join_sql` |
| 维度取值域 | ✅ `sem_dimension.value_map` |
| 口径说明 | ✅ `sem_metric.caliber` / `sem_rule` |
| **filter 算子体系** | ❌ 仅 `=` / `!=` / `in` |
| **JOIN 路径推导** | ❌ 靠 `join_sql` 硬编码片段 |
| **规约 → SQL 编译器** | ❌ 无 |

### 5.4 代价与风险

- 要写编译器，且要处理**不可加指标**（毛利率、完成率这类比率不能跨维度 `SUM`）——语义层的 `agg_default='NONE'` 已经在暗示这个约束，编译器必须尊重它；
- 表达力有上限，长尾 ad-hoc 问法仍需逃逸到 SQL 生成；
- **`join_sql` 是硬编码片段**，多维度组合时可能重复 JOIN 同一张维表，编译器需要去重。

### 5.5 关键建议

**保留 Text2SQL 作为逃逸通道。** 规约覆盖不了的问题回落到现在的生成路径——不要试图让规约覆盖 100% 的问法，那是 Metric Layer 项目最常见的失败原因。

### 5.6 验收

- `scripts/eval/run_eval` 的 100 条评测集上，规约覆盖率 ≥ 70%，且覆盖部分的 SQL 成功率 100%；
- 未覆盖部分走 Text2SQL，整体成功率不低于改造前；
- 「目标被放大 585 倍」类口径错误在覆盖范围内不复现。

## 6. 附录：`QuerySpec` 字段草案（阶段 3）

```python
@dataclass
class Filter:
    dim: str
    op: str          # = / != / in / not_in / like
    value: Any       # 标量（= / !=）或数组（in / not_in）

@dataclass
class Having:
    """对聚合结果的二次过滤 —— 当前 Slots 完全缺失这一类。"""
    metric: str
    op: str          # > / >= / < / <= / between / =
    value: Any       # between 时为 [low, high]

@dataclass
class QuerySpec:
    metrics: list[str]
    dimensions: list[str]
    filters: list[Filter]
    having: list[Having]
    time_range: dict          # {type: year|quarter|last_months, value}
    compare: Optional[str]    # yoy / mom / qoq
    order: Optional[dict]
    limit: Optional[int]
```

与现有 `Slots` 的差异只有两处：**`filters` 算子体系扩展**（`like` / `not_in`）+ **新增 `having`**。因此阶段 3 可以平滑演进——`Slots` 加两个字段即可，不需要推翻重来。

## 7. 贯穿各阶段的三条原则

1. **兜底是增益，不是依赖。** 任何一层失效都必须静默回落到上一层，且回落后的行为与没做这层时一致。每一层都要有对应的「关闭开关 + 回归测试」。

2. **模型只能在语义层给定的集合里做选择。** 无论是 LLM 抽取（阶段 1）还是向量召回（阶段 2），输出都必须过语义层白名单。**语义层是唯一的真理来源**，这既是准确率保障，也是安全保障。

3. **闭集用规则，开集用语义。** 不要为了「统一」把时间和条数也交给模型——闭集字段的正则覆盖是完备的、确定的、零成本的，换成模型只会更慢更贵更不可控。
