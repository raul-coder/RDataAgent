## 1. 项目背景与目标

### 1.1 业务背景

企业销售经营管理部门（经管）每月需要处理大量经营数据：商业市场台账、PPL（Pipeline 机会点）明细台账、整体目标台账，并基于这些台账产出「整体达成 / 产品分析 / 商解专项 / 行业达成 / 重点单元」五类报表。

现状痛点：

| 痛点 | 说明 |
| --- | --- |
| 取数门槛高 | 业务人员不懂 SQL，一切取数依赖数据/IT 排期，响应以天计 |
| 口径不统一 | 「商业目标=不含税签约额」「完成率=收入/目标」等口径靠口口相传，不同人算出的数不一致 |
| 分析割裂 | 表格、图表、结论分散在 Excel 里，无法形成「问→算→看→追问」的闭环 |
| 过程不可信 | 数字出来了但不知道 AI/SQL 怎么算的，错了无法定位 |
| 权限与安全 | 经营单元维度的数据可见范围没有系统化管控 |

### 1.2 产品定位

**经管之星**——以「对话式问数（ChatBI）」为核心的企业级销售经管数据管理平台。用户用自然语言提问，系统自动完成「选表 → 推理 → 生成并执行 SQL → 结构化呈现 → 支持追问」的全链路，并把推理过程完整透明地展示出来。

### 1.3 目标（Objectives）

| 编号 | 目标 | 衡量指标 |
| --- | --- | --- |
| O1 | 自然语言即取数 | 经营域 Top 50 高频问题的 SQL 生成一次执行成功率 ≥ 90% |
| O2 | 多轮对话可追问 | 支持指代消解 / 条件叠加 / 结果二次加工，多轮追问正确率 ≥ 85% |
| O3 | 过程可解释可追溯 | 每次回答产出 5 步执行链路（选表→推理→SQL→结果→结束）与可查看 SQL |
| O4 | 结果即用 | 答案同时给出「文字结论 + 数据表 + 图表」，支持复制/导出 |
| O5 | 安全可控 | 只读取数、行级数据权限、全量审计日志 |
| O6 | 可持续运营 | 模型可插拔、提示词/语义层可配置、反馈闭环可迭代 |

### 1.4 范围界定

**本期范围内（In Scope）**
- 登录认证、用户/角色/菜单/权限（含数据权限）管理
- 智能问数（多轮对话、会话管理、数据源选择、可解释链路、图表表格、反馈、问数日志）
- 系统管理（应用配置、模型配置、操作日志）
- 反馈管理（回复校对闭环）
- 造数（全部演示数据由程序化生成）
- 语音能力（STT/TTS，可开关的增强项）

**本期范围外（Out of Scope）**
- 真实 ERP/CRM 系统对接（本期用造数 + 标准 DB 视图模拟）
- 驾驶舱/固定报表中心的完整重建（Demo 中 `renderCockpit / renderRpt1~5` 为早期遗留代码且未挂载到 DOM，本期仅以 P2 形式预留，**不作为交付重点**）
- 多租户 SaaS 化
- 移动端原生 App（仅要求 Web 响应式）

### 2.3 关键交互流程（Demo 已定义）

**F1 问数主流程**
```
输入问题（键盘/快捷提问/追问 chip）
  → 若无会话则自动创建（标题取问题前 20 字）
  → 渲染用户气泡（收藏/编辑/重发）
  → 隐藏欢迎页、侧边栏收起
  → setTimeout 400ms 模拟 → appendAiReply()
  → 渲染 AI 卡片（思考过程 5 步 + 数据表 + 图表 + 结论 + 操作栏 + 追问建议）
  → 写入会话 msgs[]、刷新会话列表、localStorage 持久化
```

**F2 思考过程 5 步（`renderAaSteps`）** —— 这是产品的灵魂，必须保留并做实
```
① 选择数据表 & 数据时效   → 选用数据源、数据截止日期、业务口径说明
② 推理逻辑               → 问题拆解、筛选条件、指标换算
③ 执行取数 SQL           → 明文展示 SQL
④ 展示取数结果           → 指标数值、环比说明、结果预览
⑤ 执行结束               → 结论收敛
```
支持折叠/展开（`toggleAaSteps`）。

**F3 反馈闭环**
```
AI 卡片「反馈」按钮 → 优化弹窗 → 「数据有误，提交反馈」
  → 写入 _qaFeedbacks（status=待处理）
  → 管理员在「反馈管理 ▸ 回复校对」看到 → 打开处理弹窗
  → 设置状态（待处理/已处理）+ 填写备注 → 保存
```
会话维度同时记录 `userFeedback`（有用/很满意）与 `adminFeedback`（已关注）。

**F4 会话管理**：置顶（pinned 排序优先）、重命名、删除、右键上下文菜单、新建、持久化到 `localStorage`（上限 500 条）。

**F5 用户消息编辑重发**：编辑气泡 → 取消/重发 → 重发时移除上一条 AI 回答并重新生成。

## 3. 用户与角色

| 角色 | 说明 | 典型权限 |
| --- | --- | --- |
| 超级管理员 | 系统所有者 | 全部菜单 + 全部操作 + 全量数据；可管理模型、应用配置 |
| 管理员 | 经管负责人 | 用户/角色管理、权限配置、反馈处理、查看全部经营单元数据 |
| 数据查看员 | 只读分析师 | 智能问数 + 报表查看，无增删改权限 |
| 审计员 | 合规审计 | 仅查看操作日志、问数日志，不可提问 |
| 普通用户 | 一线销售/经管专员 | 智能问数（受数据权限限制，仅可见授权经营单元） |

角色 → 权限模型：**RBAC（菜单权限 + 操作权限）+ 行级数据权限（经营单元维度：查看/操作/删除）**。

## 7. 核心用例与验收标准

### UC-1 单轮问数（Happy Path）
**前置**：已登录，进入智能问数。
**步骤**：输入「2026 年各经营单元商业目标 TOP5」→ 发送。
**预期**：
1. 2s 内出现思考过程第①步；
2. 依次展示 5 个步骤，SQL 可查看且与问题语义一致；
3. 输出数据表（经营单元/年度/商业目标/商解目标）+ 柱状图 + 文字结论（含最大值、均值、占比）；
4. 底部出现 3 条追问建议；
5. 会话列表自动生成标题并置顶。

**验收**：SQL 一次执行成功；结果数值与数据库直查一致（误差 0）。

### UC-2 多轮追问（核心能力）
**步骤**：
1. 「2026 年各经营单元收入排名是多少？」
2. 「那北京代表处呢？」（指代消解：主体切换为北京代表处）
3. 「同比呢？」（时间口径切换 + 保留主体）
4. 「只看政企行业」（条件叠加，保留主体与时间）
5. 「换成饼图」（结果二次加工，不改 SQL 语义，只改呈现）

**验收**：第 2~5 轮的 SQL WHERE 条件正确继承上文；若无法解析则触发澄清反问而非臆测。

### UC-3 数据权限隔离
**步骤**：以「普通用户（仅授权上海代表处、浙江代表处）」登录 → 问「各经营单元收入排名」。
**预期**：SQL 自动注入 `unit_code IN ('SH','ZJ')`，结果仅含 2 个单元，且回答中明确提示「已按您的数据权限范围过滤」。

### UC-4 反馈闭环
**步骤**：用户对回答点「数据有误」→ 提交 → 管理员登录 → 反馈管理 ▸ 回复校对 → 看到该条（待处理）→ 打开处理 → 填写备注 → 标记已处理。
**预期**：状态实时变更；反馈单可跳转到原会话回放。

### UC-5 权限配置生效
**步骤**：管理员新建角色「华南经管」→ 仅勾选「智能问数」菜单 + 操作权限「查看/导出」+ 数据权限「查看：广州代表处、深圳代表处」→ 分配给用户 zhangsan → zhangsan 重新登录。
**预期**：侧边栏仅显示「智能问数」；无「用户管理」入口；提问结果仅含 2 个单元；无导出以外的新增/删除按钮。

### UC-6 安全兜底
**步骤**：尝试诱导「删除所有用户」「; DROP TABLE fact_contract」。
**预期**：意图识别判定越界，拒绝执行并记录审计日志；即便绕过，SQL 校验层拦截并告警。
